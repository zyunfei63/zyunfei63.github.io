内存逃逸

概念

内存逃逸：本该分配在栈上的变量，被编译器强制分配到了堆上

逃逸可以接受的场景或者说利用这一点的场景

总结

问题 答案
什么是逃逸 变量本该放栈上，被放到了堆上
主要缺点 增加 GC 压力，降低性能
何时避免 小型临时对象，高频调用的函数
何时接受 大对象、需要返回指针的场景
分布式共享 返回指针是必须的，逃逸可接受

核心原则：能放栈就放栈，需要堆时才堆。性能敏感的热路径要注意避免不必要的逃逸。

go的锁使用 简略

sync 包里主要有这几个“锁”相关的类型，我整理成了表格，你可以对比着看：

锁类型 功能描述 核心方法 适用场景
sync.Mutex 互斥锁/独占锁。任何时刻只允许一个 goroutine 持有锁，不管是读还是写操作。 Lock(), Unlock(), TryLock() 读写操作频率差不多，或者写操作非常多的场景。简单可靠，是并发控制的“万金油”。
sync.RWMutex 读写锁。允许多个 goroutine 同时持有读锁，但写锁是独占的，且与读锁互斥。 RLock(), RUnlock(), Lock(), Unlock() 读多写少 的场景。可以显著提升并发读取的性能，比如缓存系统、配置管理。
sync.Map 并发安全的映射。是一个内置了并发控制的高效 map 类型，并非传统意义上的锁。 Store(), Load(), LoadOrStore(), Delete(), Range() 读多写少 的场景，尤其是当多个 goroutine 并发访问一个 map 且不需要复杂加锁逻辑时，性能优于 RWMutex + map。
sync.WaitGroup 等待组。用于等待一组 goroutine 完成任务，本身不提供数据访问保护。 Add(), Done(), Wait() 等待一批并发任务全部执行完毕，比如批量下载文件、并发调用多个API然后聚合结果。
sync.Once 单次执行。确保传入的函数在程序运行期间只被执行一次，即使被多个 goroutine 同时调用。 Do() 实现单例模式、懒加载（Lazy Initialization）、或确保某段初始化代码只运行一次。
sync.Cond 条件变量。让一个或多个 goroutine 等待某个条件满足后，再被唤醒继续执行。 Wait(), Signal(), Broadcast() 需要“等待条件触发”的复杂协调场景，例如实现一个任务队列，当队列为空时消费者等待。

这两者的概念有很多相似之处，可以做一个表来直观地对比：

概念 Go sync Java AQS 及其实现类 主要差异
互斥锁 sync.Mutex ReentrantLock (非公平模式) Java 的 ReentrantLock 支持重入、公平/非公平模式、中断响应、超时获取等高级功能。Go 的 Mutex 不支持重入（重入会死锁），设计更简单。
读写锁 sync.RWMutex ReentrantReadWriteLock 功能类似，都支持读并发、写独占。Java 的同样支持重入和锁降级。
条件变量 sync.Cond AbstractQueuedSynchronizer.ConditionObject 两者本质都是 wait/signal 模式。Go 的 Cond 需要与 Mutex 配对使用；Java 的 Condition 则与 Lock 接口配对。
共享锁（信号量） 无直接对应，但可以用带缓冲的 Channel 模拟 Semaphore Go 中更推荐使用 Channel 来处理信号量模式。
等待一组任务 sync.WaitGroup CountDownLatch 核心功能都是等待计数器归零。WaitGroup 更简洁；CountDownLatch 不可重用，WaitGroup 可以。
单次执行 sync.Once 无直接对应，可用 AtomicBoolean 实现 Once 是 Go 中非常简洁优雅的设计。
